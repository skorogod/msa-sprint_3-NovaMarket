# ADR: История покупок (CQRS)

### **Название задачи:** Просмотр истории покупок
### **Автор:** skorogod
### **Дата:** 01.10.2026

### **Функциональные требования**

| № | Действующие лица или системы | Use Case | Описание |
| :-: | :- | :- | :- |
| 1 | Покупатель, приложение, Сервис истории заказов | Список заказов | Покупатель открывает историю. Приложение запрашивает `GET /orders/history`. Сервис возвращает заказы постранично: дата, сумма, способ доставки, статус. |
| 2 | Покупатель, приложение, Сервис истории заказов | Детали заказа | Покупатель открывает заказ. `GET /orders/history/{id}` возвращает товары, количество, цены, итог, способ доставки и оплаты, финальный статус. |
| 3 | Покупатель, Сервис платежей, Хранилище чеков | Скачать чек | Покупатель нажимает «Скачать чек». Сервис платежей проверяет владельца заказа и отдаёт временную ссылку на PDF. |
| 4 | Покупатель, Сервис отзывов | Оставить отзыв | Покупатель пишет отзыв о товаре из заказа. Сервис отзывов знает о доставленных заказах по событию «Заказ доставлен» и отмечает отзыв как подтверждённую покупку. |
| 5 | Покупатель, Сервис корзины | Заказать снова | Покупатель нажимает «Повторить». Товары из заказа добавляются в корзину с текущими ценами, недоступные товары помечаются. |
| 6 | Сервисы заказов, платежей, доставки, Kafka, Сервис истории заказов | Обновление истории | Сервисы публикуют события. Сервис истории получает их и обновляет карточку заказа в своей БД. |

### **Нефункциональные требования**

| № | Требование |
| :-: | :- |
| 1 | Ответ на список и детали заказа — не дольше 300 мс (p95). |
| 2 | Чтение истории не нагружает Сервис заказов и его БД. |
| 3 | История открывается, даже если Сервисы платежей или доставки недоступны. |
| 4 | Изменения попадают в историю не позже чем через 5 секунд. |
| 5 | Повторное или запоздавшее событие не портит данные. |
| 6 | Цена в истории — цена на момент покупки, она не меняется вслед за каталогом. |
| 7 | Покупатель видит только свои заказы. |

### **Решение**

Используем **CQRS**: запись и чтение заказов разделены.

- **Запись** остаётся как есть: Сервис заказов ведёт заказ по саге.
- **Чтение** берёт на себя новый **Сервис истории заказов** со своей БД. Он подписан на события заказов, платежей и доставки и собирает из них готовую карточку заказа. Покупатель получает её одним запросом, без обращений к другим сервисам.

#### Что меняется

| Элемент | Изменение |
| :- | :- |
| Сервис истории заказов (новый) | Получает события из Kafka, хранит карточки заказов, отдаёт `GET /orders/history` и `GET /orders/history/{id}`. |
| БД истории заказов (новая) | MongoDB, коллекция `order_history`. Один документ на заказ со всеми данными для экрана, индекс `{customerId: 1, createdAt: -1}`. |
| Хранилище чеков (новое) | S3. Сервис платежей кладёт сюда PDF-чеки. |
| Сервис заказов | В событие `OrderCreated` добавляются товары, цены и способ доставки. |
| Сервис платежей | В `PaymentSucceeded` добавляется способ оплаты. Новое событие `ReceiptIssued` (чек готов). |
| Сервис доставки | В `ShipmentCreated` и `ShipmentDelivered` передаются способ доставки, трек и дата получения. |
| Сервис отзывов | Подписывается на `ShipmentDelivered`. |
| API Gateway | Новый маршрут `/orders/history` в Сервис истории заказов. |

#### Как хранятся заказ и товары

- **Товары** (название, цена, фото, описание) хранятся в БД каталога, их владелец — Сервис каталога.
- **Запись (БД заказов, PostgreSQL).** Таблицы `orders` и `order_items`. От товара хранится только `product_id`, количество и цена.
- **Чтение (БД истории, MongoDB).** Один документ на заказ. Товары лежат в нём массивом `items` с копией названия, фото, количества и цены на момент покупки. Копия приходит в событии `OrderCreated`, в каталог за товарами никто не ходит. Если цена в каталоге изменится, в истории останется цена покупки. По `productId` работают «Оставить отзыв», «Заказать снова» и переход в карточку товара.

```json
{
  "_id": "o-5001",
  "customerId": "c-42",
  "createdAt": "2026-09-20T12:30:00Z",
  "status": "DELIVERED",
  "total": 8570,
  "deliveryMethod": "Курьер",
  "paymentMethod": "Карта ··1234",
  "items": [
    { "productId": "p-101", "name": "Наушники X", "photo": "https://…/p-101.jpg", "quantity": 2, "price": 3990 },
    { "productId": "p-205", "name": "Чехол", "photo": "https://…/p-205.jpg", "quantity": 1, "price": 590 }
  ],
  "trackNumber": "RU123456",
  "deliveredAt": "2026-09-28",
  "receiptAvailable": true
}
```

#### Откуда берутся данные

| Событие | От кого | Что обновляет |
| :- | :- | :- |
| `OrderCreated` | Заказы | Создаёт карточку: дата, товары, цены, сумма, способ доставки |
| `OrderStatusChanged`, `OrderCancelled` | Заказы | Статус |
| `PaymentSucceeded`, `PaymentRefunded` | Платежи | Способ оплаты, возврат |
| `ReceiptIssued` | Платежи | Признак «чек есть» |
| `ShipmentCreated`, `ShipmentDelivered` | Доставка | Трек, дата доставки, статус «Доставлен» |

#### Как обрабатываются события

- У каждого события есть номер версии. Если пришло старое событие или повтор, оно пропускается.
- События одного заказа идут в одну партицию Kafka, поэтому приходят по порядку.
- При запуске сервис один раз загружает старые заказы из БД сервисов, дальше обновляется по событиям.
- Если данные испортились, историю можно собрать заново: заново прочитать события из Kafka.

#### Почему так

1. Данные для экрана лежат в трёх сервисах. Быстро отдать их одним запросом можно, только если собрать их заранее.
2. Нужные события уже есть (сага из задания 1). Достаточно добавить нового подписчика и несколько полей.
3. История почти не меняется после доставки, поэтому задержка в несколько секунд не страшна.
4. Для БД истории выбрана MongoDB:
   - каждый заказ — готовый документ, он сохраняется как есть;
   - схема гибкая: новые поля (например, данные возврата) добавляются без миграций;
   - история растёт без ограничений, а MongoDB легко делится на шарды по `customerId`;
   - все заказы покупателя лежат на одном шарде, поэтому список отдаётся одним запросом.

### **Альтернативы**

#### 1. API Composition
Gateway на каждый запрос ходит в Заказы, Платежи и Доставку и склеивает ответ.

- **Плюсы:** просто, нет новой БД, данные всегда свежие.
- **Минусы:** ответ ждёт самый медленный сервис. Если один сервис упал, история не открывается. Вся нагрузка ложится на Сервис заказов, который и так занят сагой.

Отклонено: не выполняются требования 1–3.

#### 2. Репликация БД заказов
История читается с копии (реплики) БД заказов.

- **Плюсы:** делается средствами СУБД, почти без кода, снимает чтение с основной БД.
- **Минусы:**
  - В БД заказов нет способа оплаты, чека и данных доставки, поэтому всё равно придётся ходить в другие сервисы.
  - У реплики та же структура, что у основной БД, отдельно под чтение её не настроить.
  - Реплика тоже отстаёт от основной БД.
  - Записи саги в основную БД она не уменьшает.

Отклонено: решает только нагрузку на одну БД, но не сбор данных из разных сервисов. Реплику можно добавить позже, уже для БД истории.

#### 3. Event Sourcing
Сервис заказов хранит не текущее состояние, а все события заказа.

- **Плюсы:** полная история изменений, любые представления строятся из событий.
- **Минусы:** придётся переписать Сервис заказов. Это сложно в разработке и отладке. Данные платежей и доставки всё равно лежат в других сервисах.

Отклонено: слишком дорого для этой задачи.

#### 4. PostgreSQL с JSONB для БД истории
Та же модель чтения, но заказ хранится в PostgreSQL как JSON-поле.

- **Плюсы:** тот же стек, что у остальных сервисов, команда его знает.
- **Минусы:** делить такую БД на шарды при росте истории сложнее, документ приходится раскладывать по колонкам и JSON-полю.

Отклонено: MongoDB проще масштабировать под растущую историю.

### **Недостатки, ограничения, риски**

| Риск | Что делаем |
| :- | :- |
| История отстаёт от реального статуса на несколько секунд. | Экран нужен для завершённых заказов. Текущий статус активного заказа отдаёт Сервис заказов. Следим за задержкой и ставим алерт. |
| Данные заказа хранятся дважды и могут разойтись. | Раз в сутки сверяем историю с Сервисом заказов. Историю можно пересобрать. |
| Нужно менять события в трёх сервисах. | Только добавляем новые поля, старые не трогаем. |
| Ещё один сервис и БД в эксплуатации. | Сервис на Go, те же шаблоны деплоя и мониторинга. |
| MongoDB — новая технология в стеке, команде нужен опыт её эксплуатации. | Берём managed-сервис или готовый оператор для Kubernetes, бэкапы и мониторинг по шаблону. |
| Ошибка в сервисе истории испортит много записей. | Есть инструкция пересборки, события в Kafka хранятся достаточно долго. |
| Число заказов растёт. | Постраничная выдача, шарды MongoDB по `customerId`. |
| Сервис платежей недоступен, и чек не скачать. | История при этом открывается. Приложение предлагает повторить позже. |
